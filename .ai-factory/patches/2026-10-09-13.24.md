# Add Google Gemini as an LLM provider via its OpenAI-compatible API

**Date:** 2026-10-09 13:24
**Files:** server/src/config.ts, server/src/agent/openai-compat.ts (was dahl.ts), server/src/agent/dahl.ts, server/src/agent/gemini.ts, server/src/agent/dahl-wire.ts, server/src/agent/llm.ts, server/src/http/server.ts, server/scripts/count-prompt-tokens.ts, README.md, .env.example, tests (config, dahl-wire, gemini)
**Severity:** medium

## Problem

There was no way to run the agent on Google Gemini. `LLM_PROVIDER=gemini` failed at startup with
`LLM_PROVIDER must be "dahl", "anthropic" or "ollama", got "gemini"`.

## Root Cause

The provider seam had only three hard-coded providers. The Dahl adapter, which is a generic
OpenAI chat-completions to Anthropic tool-runner bridge, was tied to Dahl. It used Dahl error
classes, `dahlApiKey()` and the `agent.dahl` log scope. The shared wire layer also refused every
image block, because no Dahl model has vision. So a second OpenAI-compatible provider could only
be added by copying about 500 lines.

## Solution

- `dahl.ts` became `openai-compat.ts`, an engine that takes a `ProviderProfile`: label, key getter,
  `allowImages`, and error-class constructors. The base classes are `ChatApiError`,
  `ChatConnectionError` and `ChatMissingKeyError`, so retry logic uses `instanceof` on the bases.
- `dahl.ts` is now a thin wrapper with the same public API (`DahlApiError` and the rest are
  subclasses). The existing Dahl tests pass unchanged.
- `gemini.ts` is the same kind of wrapper. It points at
  `https://generativelanguage.googleapis.com/v1beta/openai`, uses `GEMINI_API_KEY` (falling back to
  `GOOGLE_API_KEY`), and sets `allowImages: true`.
- `toOpenAiMessages(..., { allowImages })` turns base64 or URL image blocks into `image_url` parts.
  User messages with text only stay a plain string, and the default is unchanged (images throw).
- `llm.ts`: `createAgentClient` routes `gemini`, `createLlmClient` is narrowed to anthropic/ollama,
  and `describeGeminiError` gives Russian texts for 400 bad key, 403, 404 model, 429 quota and 5xx.
  `preflightGemini` (GET /models with the key) runs at startup.

## Prevention

- When a second provider needs code that already exists for another provider, parameterize it.
  Don't copy it. Keep the provider modules as thin wrappers that only supply naming, keys and
  capability flags.
- A capability like vision should be a flag on the provider profile, not a hard-coded throw in a
  shared layer.
- Narrow union parameters with `Extract<…, {provider: "a" | "b"}>`, not `Exclude<…>`. With
  `Exclude`, a newly added union member slips silently into the wrong branch. Here, `gemini` would
  have typechecked into the Ollama path of `createLlmClient`.
- Not verified live (no key in this environment): streaming `usage` with `stream_options`, the
  granularity of tool-call deltas, and the error body shape of the Gemini OpenAI-compatible
  endpoint. Check them with a real `GEMINI_API_KEY` by running `smoke:s1`.
