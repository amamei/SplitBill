# Хакатон: Agentic UI на примере Split Bill

## 1. Цель

Не приложение, а сравнение. Четыре человека собирают одно и то же приложение для
дележа счёта, каждый на своём инструменте agentic / generative UI. На выходе —
четыре работающих демо и сводная таблица: что каждый инструмент умеет, где ломается и
для каких задач мы бы его взяли.

Agentic UI здесь — интерфейс, который агент выбирает или собирает в рантайме в ответ
на запрос, а действия пользователя в этом интерфейсе возвращаются агенту.

## 2. Инструменты

Основная четвёрка покрывает четыре разных подхода, поэтому сравнение получится
содержательным:

| # | Инструмент | Подход | Стек | Что проверяем |
|---|---|---|---|---|
| 1 | **MCP Apps** (наследник mcp-ui) | UI пишет разработчик, сервер отдаёт его как `ui://` ресурс, хост рисует в sandbox-iframe | TS, любой фронт внутри iframe | Базовая линия: заранее написанный UI, агент только выбирает и наполняет |
| 2 | **A2UI** (Google, v0.9) | Агент выдаёт декларативный JSONL из каталога компонентов, клиент рисует нативно | Рендереры: Lit, Angular, React, Flutter | Декларативная спека, переносимость между платформами |
| 3 | **OpenUI** (Thesys) | Агент пишет компактный OpenUI Lang по библиотеке React-компонентов, стриминговый рендерер | React | Свой набор компонентов как контракт, стриминг, расход токенов |
| 4 | **Prefab** (FastMCP) | Агент пишет Python-DSL, UI собирается на лету; доставляется как MCP App | Python | Генерация UI кодом, без фронтенда |

MCP Apps и Prefab живут в одном хосте (оба — MCP Apps), но проверяют разное: в №1 UI
написан руками заранее, в №4 его пишет модель. Участник №1 **не** использует Prefab и
другие генераторы — иначе базовой линии не будет.

Кандидаты на пятое место или на замену:

- **CopilotKit + AG-UI** — не спека UI, а транспорт между агентом и приложением; умеет
  рендерить и A2UI, и MCP Apps. Самый «продуктовый» вариант: агент внутри своего
  приложения, общий стейт, human-in-the-loop. Первый кандидат, если появится пятый
  участник.
- **Vercel json-render / AI SDK** — JSON-спека по своему каталогу компонентов в
  Next.js; ближайший аналог OpenUI от Vercel.
- **Tambo** — React: модель выбирает из зарегистрированных компонентов и заполняет
  пропсы.
- **OpenAI Apps SDK** — приложения внутри ChatGPT, построены на MCP Apps; имеет смысл
  только если интересен ChatGPT как канал.

## 3. Общие правила

- Одна модель у всех (договориться до старта) — иначе сравниваем модели, а не
  инструменты.
- Деньги считает код, не модель. Модель вызывает тулы и рисует результат.
- Суммы — целые числа в минорных единицах (бани/копейки). Никаких float.
- Хранилище — память процесса. Авторизации, БД, деплоя нет.
- Свой AI-ассистент для написания кода использовать можно и нужно; заметки о том, как
  он справился с документацией инструмента, идут в отчёт.
- Каждый ведёт лог затыков по ходу, а не по памяти в конце.

## 4. Доменный контракт

Одинаковый у всех, реализуется в своём стеке (логика — ~150 строк).

```
Person { id, name }
Item   { id, title, price, paidById, split }      // price в минорных единицах
Split  = { type: "equal",  personIds[] }           // поровну; по умолчанию все участники
       | { type: "exact",  amounts: {personId: amount} }   // абсолютные суммы
       | { type: "shares", weights: {personId: weight} }   // относительные доли
Bill   { id, title, currency, people[], items[] }
```

Плательщик — свойство позиции. Отдельных сущностей «оплата» и «сервис» нет: чаевые —
обычная позиция со своим плательщиком и способом деления. Так «один заплатил за
кальяны, второй за еду, третий за чаевые» выражается без дополнительных полей.

Тулы агента:

| Тул | Что делает |
|---|---|
| `create_bill(title, people[], items[])` | Создаёт счёт |
| `add_person(billId, name)` | Добавляет участника |
| `rename_person(billId, personId, name)` | Переименовывает |
| `remove_person(billId, personId)` | Удаляет; ошибка со списком позиций, если на участника есть ссылки |
| `add_item(billId, item)` | Добавляет позицию |
| `update_item(billId, itemId, patch)` | Меняет название, цену, плательщика, способ деления |
| `remove_item(billId, itemId)` | Удаляет позицию |
| `get_summary(billId)` | Доли, балансы, кто кому сколько должен |

Правила:

1. `equal` — цена делится поровну между `personIds`. Новая позиция без указания
   способа — `equal` на всех участников.
2. `exact` — сумма `amounts` обязана равняться цене, иначе тул возвращает ошибку с
   расхождением.
3. `shares` — цена делится пропорционально весам (целые положительные числа; проценты
   — частный случай с суммой 100).
4. Неделимый остаток раздаётся по 1 минорной единице участникам деления в порядке
   списка людей.
5. Участника нельзя удалить, пока он плательщик или участник деления хотя бы одной
   позиции. Новый участник в существующие позиции сам не попадает.
6. Баланс = заплатил − должен. Итог — список переводов «кто → кому → сколько»,
   обнуляющий балансы не более чем за N−1 перевод.

## 5. Сценарии

Обязательные — S1–S6. Каждый показывается на демо вживую.

**S1. Счёт из текста.** Пользователь пишет свободным текстом, кто был, что заказали и
кто за что платил. Агент создаёт счёт и показывает его.

**S2. Управление участниками.** Добавить, переименовать, удалить — через UI. Удаление
участника, на которого ссылаются позиции, не проходит: интерфейс показывает, какие
позиции мешают, и даёт их поправить.

**S3. Управление позициями.** Добавить, изменить название и цену, удалить — через UI,
без набора текста в чат.

**S4. Способ деления.** У каждой позиции переключается один из трёх способов —
поровну, абсолютные суммы, относительные доли — и поля ввода меняются под способ.
Для `exact` видно, сколько осталось распределить.

**S5. Плательщики и итог.** У каждой позиции выбирается плательщик. Экран итога: доля
каждого, сколько внёс, баланс и список «кто кому сколько должен».

**S6. Правка словами поверх готового UI.** «Гена тоже курил, одна доля» — существующий
интерфейс обновляется, итог пересчитывается. Фиксируем: обновился на месте или
перерисовался целиком.

Дополнительные (по убыванию пользы для сравнения):

**S7. Незапланированный запрос.** «Покажи диаграммой, кто сколько потратил» — экрана
под это никто не готовил. Главный тест на «генеративность»: что инструмент сделает сам.

**S8. Действие из UI обратно агенту.** Кнопка «напомнить Вике» → агент пишет текст
напоминания с её суммой и получателями.

**S9. Фото чека.** Загрузка картинки → позиции.

**S10. Стриминг.** UI появляется по мере генерации, а не одним куском.

## 6. Контрольный пример

Все прогоняют его на демо; цифры должны совпасть.

Люди: Аня, Боря, Вика, Гена.

| Позиция | Цена | Платил | Деление |
|---|---|---|---|
| Еда | 1200 | Боря | поровну, все |
| Кальяны | 800 | Аня | доли: Аня 2, Боря 1, Вика 1 |
| Вино | 600 | Аня | суммы: Аня 250, Боря 250, Вика 100 |
| Чаевые | 260 | Вика | поровну, все |

| | Еда | Кальяны | Вино | Чаевые | Должен | Заплатил | Баланс |
|---|---|---|---|---|---|---|---|
| Аня | 300 | 400 | 250 | 65 | 1015 | 1400 | +385 |
| Боря | 300 | 200 | 250 | 65 | 815 | 1200 | +385 |
| Вика | 300 | 200 | 100 | 65 | 665 | 260 | −405 |
| Гена | 300 | 0 | 0 | 65 | 365 | 0 | −365 |
| Итого | 1200 | 800 | 600 | 260 | 2860 | 2860 | 0 |

Кто кому должен — три перевода, например: Вика → Аня 385, Вика → Боря 20,
Гена → Боря 365. Конкретный набор может отличаться; проверяем балансы и число
переводов.

После S6 («Гена тоже курил, одна доля» → веса 2/1/1/1, кальяны 320/160/160/160):

| | Должен | Заплатил | Баланс |
|---|---|---|---|
| Аня | 935 | 1400 | +465 |
| Боря | 775 | 1200 | +425 |
| Вика | 625 | 260 | −365 |
| Гена | 525 | 0 | −525 |

Проверки на края:

- Округление: позиция 100 поровну на Аню, Борю, Вику → 33.34 / 33.33 / 33.33.
- `exact` с суммой 590 при цене 600 → ошибка «не распределено 10».
- Удаление Гены в исходном примере → ошибка со ссылками на «Еду» и «Чаевые».

## 7. Что сравниваем

Каждый заполняет по своему инструменту. Оценки 1–5 плюс одна строка обоснования.

| Критерий | Что смотрим |
|---|---|
| Время до первого экрана | От пустой папки до отрисованного S1, в минутах |
| Покрытие сценариев | Какие из S1–S10 сделаны, какие невозможны и почему |
| Кто автор UI | Разработчик заранее / модель из каталога / модель свободно |
| Интерактивность | Как действие в UI попадает в стейт и к агенту; нужен ли круг через модель |
| Формы и валидация | S2, S4: смена полей под способ деления, показ ошибки тула в UI |
| Обновление на месте | S6: патч или полная перерисовка |
| Незапланированное | S7: результат без доработки кода |
| Надёжность | Доля битых или кривых рендеров на 10 прогонах S1 |
| Скорость и токены | Время до отрисовки и выходные токены на S1 и S5 |
| Контроль внешнего вида | Можно ли натянуть свою дизайн-систему |
| Где запускается | Свой сайт / чат-хост (Claude, ChatGPT, VS Code) / мобилка |
| Зрелость | Документация, версия, что сломалось по дороге |
| DX с AI-ассистентом | Справился ли ассистент с инструментом по докам или галлюцинировал API |

## 8. Что сдаём

1. Папка `<tool>/` в общем репозитории с README: как запустить одной командой.
2. Демо 7 минут: S1–S6 на контрольном примере, затем S7.
3. `<tool>/REPORT.md`:
   - таблица из раздела 7;
   - три вещи, которые понравились, три, которые мешали;
   - лог затыков;
   - вердикт: для каких задач взял бы, для каких нет.
4. Общий итог после демо: сводная таблица 4 × критерии и рекомендация команде.

## 9. Тайминг (один день)

| Время | Что |
|---|---|
| 0:00–0:30 | Установка: общая модель, ключи, раздача инструментов |
| 0:30–1:30 | Hello world инструмента + доменные тулы, прогон контрольного примера тестом |
| 1:30–5:00 | S1–S6 |
| 5:00–5:30 | S7 и дальше по списку |
| 5:30–6:00 | Замеры (раздел 7), REPORT.md |
| 6:00–7:00 | Демо 4 × 7 минут + вопросы |
| 7:00–7:30 | Сводная таблица и выводы |

Отсечка: если к 1:30 инструмент не нарисовал ни одного экрана — зовём остальных на
15 минут; не помогло — переходим на запасной из раздела 2, а причину пишем в отчёт
(это тоже результат).
